# Gateway 入口边界

消费者通过 `POST /api/checkout` 结算。Commerce 从登录身份和当前商品数据构造内部订单请求，不能让消费者通过旧实验接口指定其他用户或任意成交价格。

默认拒绝以下两个历史创建入口，即使调用者已登录：

- `POST /api/orders`
- `POST /api/orders/redis`

网关返回 HTTP 403 和 `LEGACY_ORDER_ENTRY_DISABLED`，不会转发创建请求。订单列表、本人订单详情、取消、Commerce 结算及模拟支付仍遵守原有鉴权与路由。旧 Order 接口和请求结构保留，但不作为默认商城消费入口。

订单路由下的 POST 默认只允许现有的“数字订单号/cancel”操作；未知或含点段的其他写入路径同样拒绝，避免下游 Servlet 容器规范化路径后绕过两个历史创建入口的保护。未来增加消费者订单写接口时，需要显式审核并加入允许范围。

## 受控本地实验

只有在隔离的本地实验环境中，才可显式设置环境变量 `GATEWAY_LEGACY_ORDER_CREATE_ENABLED=true` 后重启 Gateway。默认值为 `false`，消费者环境必须保持关闭；启用时启动日志会打印警告。

该开关只是解除入口隔离，**不是鉴权或用户/价格授权机制**。启用后仍要求有效 JWT，但历史创建请求体中的用户、价格仍由实验调用方指定，因此不能把开启开关的 Gateway 暴露给普通消费者。即使匿名白名单被扩大，两个历史创建入口也不会因此免除 JWT 验证。JWT 与内部令牌继续由环境配置提供，不在文档或配置中写真实值。

Gateway 继续剥离客户端的 `X-User-Id`、`X-Username` 和 `X-Internal-Service-Token`，认证后注入可信用户头，并在 Order 路由上重新设置内部令牌。Order 直连入口的内部令牌过滤器未修改；部署时仍须限制业务服务端口的网络访问。不要以持有内部令牌或打开实验开关为理由，让真实消费者绕过 Commerce 的金额与归属校验。

## 验证范围

`AuthenticationGlobalFilterTest` 覆盖默认拒绝两类创建、尾斜杠、矩阵参数和点段路径、正常查询/取消/结算/模拟支付放行、显式开启后仍强制认证及伪造头剥离。这是无数据库的过滤器测试，不代替真实 Gateway 到各服务的部署验收；后者还应确认默认关闭、正常结算成功和直连 Order 无内部令牌被拒绝。
