## 一、这个项目解决什么实际问题

### 场景

一个 SKU 备货 1000 件，大促零点开售，瞬间涌入十万级请求。

这个场景下会出事的地方，不是"功能没写"，而是**功能在并发下失效**。单线程跑测试全绿，上了量就崩。这是后端工程和"会写 CRUD"之间真正的分水岭，也是面试反复问同一组问题的原因。

### 六个真实失效模式

**一、超卖。** 卖出 1200 件，仓库只有 1000 件。后果是砍单赔付或紧急补货，直接损失钱和商誉。技术成因：库存检查和扣减是两步，两步之间被其他线程插入。

**二、库存被无效占用。** 用户下单不付款。如果库存一直锁着，真正想买的人看到"已售罄"。这个损失是隐形的——没人投诉，但转化率实实在在掉了。

**三、重复扣减。** 支付网关的回调一定会重试：网络超时重发、对账补发、人工重推。同一笔支付回调三次，不做幂等就扣三次库存、发三次货。这不是小概率事件，是支付集成的常态。

**四、跨服务状态不一致。** 订单服务写入成功，调库存服务超时。订单显示已创建，库存没扣。用户付了钱没有货，或者有货但账对不上。超时的可怕之处在于你不知道对方到底执行了没有。

**五、热点竞争拖垮数据库。** 所有请求打同一行，InnoDB 行锁排队，响应时间从 10ms 涨到 2s，连接池耗尽，线程阻塞，整个服务雪崩——而且会顺着调用链把上游一起拖下水。

**六、多 SKU 加锁顺序不一致导致死锁。** 两个订单以相反顺序更新相同 SKU 时会形成循环等待，数据库只能回滚其中一个事务；如果上层没有正确重试或补偿，就会出现下单失败和状态残留。

### 这个项目的定位

**不是做一个电商系统，是把上面六个失效模式逐个复现、修复、量化。**

区别很重要：前者的产出是"我做了个商城"，后者的产出是"我在 300 并发下复现了 87 件超卖，改成原子扣减后归零"。后者才有人听得进去。

## 二、功能怎么解决这些问题

每个功能对应一个失效模式。**"关键洞察"那一栏是面试实际要问的东西**，功能本身谁都会写。

### 2.1 原子扣减 → 解决超卖

把"读库存 → 判断够不够 → 写回去"三步压缩成一条带条件的 UPDATE，让数据库在持有行锁期间完成判断。

**关键洞察：** 判断条件写在 Java 里还是写在 SQL 的 `where` 里，差别不在代码风格，在于判断发生时**有没有人能插进来**。写在 Java 里，判断和写入之间隔着一次网络往返和一次事务调度；写在 `where` 里，判断和更新在同一次行锁持有期内完成，物理上没有间隙。

**常见误解：** 很多人以为加 `@Transactional` 就能防超卖。不能。事务保证的是原子性和隔离性，不是互斥——RR 隔离级别下两个事务各读各的快照，都看到 100，都写回 99。这题面试问得极多。

### 2.2 库存三态 + 超时关单 → 解决库存无效占用

库存拆成可售（stock）、锁定（lock_stock）、实际（两者之和）。下单时可售转锁定，支付成功后锁定转实扣，超时未支付则锁定转回可售。独立的锁定记录表维护每一笔预占的状态流转。

**关键洞察：** 延迟任务到期时**不能无脑关单**，必须先复查订单当前状态——因为支付可能刚好在这一刻到达。关单和支付回调是两个并发写同一行订单的路径，必须用状态机约束：只有「待支付」才能转「已取消」，用带状态条件的 UPDATE 让数据库裁决谁先谁后。

### 2.3 幂等 → 解决重复扣减

以外部支付交易号做数据库唯一约束。第二次回调插入冲突，认定为重复，查询既有结果直接返回成功。

**关键洞察：** 幂等**不是**"先查一下处理过没有，没处理过再处理"——那本身又是一个"先查后写"的竞态，两个回调同时查都说没处理过。真正的幂等要让数据库的唯一约束来裁决，把冲突检测下沉到唯一索引。

### 2.4 本地消息表 → 解决跨服务不一致

把"发消息通知下游"变成"往同一个库里插一行消息记录"，和业务写入在同一个本地事务里。业务成功消息一定在，业务回滚消息一定没有。再由独立的投递任务扫表推送，失败重试。

**关键洞察：** 这是拿**实时性**换**可靠性**。消息不再是即时到达，而是最终到达。能接受这个交换，是因为库存释放、通知下游这类操作本来就不要求毫秒级。反过来，凡是要求强一致的场景（比如扣款和记账），本地消息表就不适用。

### 2.5 加锁顺序统一 → 解决并发死锁

一个订单包含多个 SKU 时，扣减前按 skuId 排序，让所有事务以相同顺序申请行锁。

**关键洞察：** 死锁的四个必要条件里，这个做法破坏的是**循环等待**。事务 A 锁了 SKU-1 等 SKU-2，事务 B 锁了 SKU-2 等 SKU-1，就成环了；统一顺序后永远只能是先到的等后到的，成不了环。

**这条的特殊价值：** 这个缺陷在 mall4cloud 里真实存在（`SkuStockLockServiceImpl.java:97,102` 循环内逐 SKU 扣减，未排序）。"读工业代码时发现的并发缺陷 + 自己复现验证 + 修复"是一个完整故事，比任何自造的难点都可信。

### 2.6 Redis 预扣 + 令牌桶限流 → 解决热点拖垮数据库

Lua 脚本在 Redis 里完成"判断 + 扣减"，把绝大部分注定失败的请求（库存已空）挡在 MySQL 之前。令牌桶同样用 Lua 实现，保证取令牌的原子性。

**关键洞察：** 限流的价值不是"扛住更多请求"，是让系统在过载时的失效形态从**全体一起慢**变成**部分快速失败**。前者是雪崩，后者是降级。这个区别面试官很在意。

**必须配套的东西：** Redis 和 MySQL 的库存会漂移（Redis 扣了但落库失败、Redis 重启丢数据），所以必须有定时对账任务输出差异清单。只做预扣不做对账，是半成品。

### 汇总

| 失效模式 | 功能 | 验证方式 | 产出数字 |
| --- | --- | --- | --- |
| 超卖 | 原子扣减 | JUnit + CountDownLatch | 超卖件数 X → 0 |
| 库存无效占用 | 三态 + 延迟关单 | 场景测试 | 库存回收延迟、关单成功率 |
| 重复扣减 | 唯一约束幂等 | 重复回调 N 次 | 状态变更次数 = 1 |
| 跨服务不一致 | 本地消息表 | 强杀服务后观察 | 最终一致恢复耗时 |
| 并发死锁 | 加锁顺序排序 | JUnit 并发多 SKU | 死锁率 X% → 0 |
| 热点拖垮 DB | Redis 预扣 + 限流 | JMeter | QPS、P99、错误率 |

## 三、技术选型

**"为什么不用别的"这一列比"用了什么"重要得多。** 面试官判断你是选型还是照抄，就看这一列。

| 功能 | 选型 | 为什么不用别的 |
| --- | --- | --- |
| 原子扣减 | 单条条件 UPDATE | 不用 `select for update`：多一次往返，锁持有时间更长。不用乐观锁 version：热点行冲突率极高，失败重试反而放大压力 |
| 超时关单 | Redisson 延迟队列 | 不用 RocketMQ 延迟消息：多一个中间件，本地开发成本翻倍，效果等价。不用定时扫表：大表全扫，延迟精度差 |
| 幂等 | 数据库唯一约束 | 不用 Redis SETNX：Redis 和 DB 不在同一事务，中间宕机会漏判 |
| 跨服务一致性 | 本地消息表 + 定时补偿 | 不用 Seata AT：AT 在分支事务上加全局锁，而热点 SKU 本就是行锁竞争点，叠加会放大瓶颈。**可选在周期 6 接上做压测对比，用数据佐证这个判断** |
| 限流 | Redis + Lua 自实现令牌桶 | 不用 Sentinel：用组件和讲得清算法，面试价值差一个量级。mall4cloud 全项目没有限流，这个缺口正是机会 |
| 服务注册与配置 | Nacos（目标态，尚未接入） | 一个组件同时解决注册和配置，比 Eureka + Config 少一个部署单元 |
| 服务间调用 | OpenFeign | — |
| 统一入口 | Spring Cloud Gateway | — |
| 持久层 | MySQL 8 + MyBatis-Plus | 需要手写原子 SQL，MyBatis 的 XML 比 JPA 更顺手 |
| 正确性测试 | JUnit 5 + CountDownLatch | 精确、可复现、随代码提交。外部压测工具难保证"同一瞬间" |
| 性能压测 | JMeter | **Postman 不是压测工具**，只用于接口调试。被问"用什么压测的"时 JMeter / wrk 是标准答案 |

语言与框架：Java 17 + Spring Boot 3.3。当前 Docker Compose 包含 MySQL、Redis、Prometheus 和 Grafana；周期 7 的四个 Java 进程通过环境变量配置静态服务 URL。Nacos 属于后续目标态，尚未进入当前 Compose。

对比 mall4cloud 需要的 Nacos + Seata + RocketMQ + Elasticsearch + Canal + Redis + MySQL 七件套，这是数量级差别。**重的从来不是"拆成几个服务"，是中间件。**

## 四、功能边界

边界不清是个人项目最大的死因——总觉得"再加一个功能会更完整"，然后永远做不完。

### 明确不做：业务广度

商品管理、搜索、购物车、优惠券与促销计算、多商户与店铺、RBAC 权限、物流与发货、退款与售后、评价。

**理由：** 这些是广度，不产生并发深度。没有任何面试官会因为你实现了购物车而加分，但它们会吃掉你一半时间。

### 明确不做：基础设施深度

分库分表、多级缓存、多仓库存与调拨、真实支付渠道对接（用 mock）、Kubernetes、服务网格、链路追踪全家桶。

**理由：** 单机规模下这些问题不会真实出现，为了写简历硬上，第一个追问就会露馅——"你分了几片？路由键怎么选的？跨片查询怎么处理？"答不上来比没写更糟。

### 规模边界

5 个测试 SKU、单仓、单机 MySQL、单机 Redis、压测机与被测服务同机。

这个边界要**主动写进简历和口述里**："单机同环境对比"。主动划定数字边界是加分项，被问出来才承认是减分项。

### 服务边界

四个服务：`gateway`（入口、全局限流）、`order-service`（下单编排、订单状态机、超时关单）、`inventory-service`（库存三态、原子扣减、Redis 预扣、对账 —— **高并发核心全在这里**）、`payment-service`（支付回调、幂等，可以做得很薄）。

### 前端

默认不做。可选一个极简 React 看板展示 QPS、P99、库存差异、限流触发——你有现成前端能力，成本低，简历上多一条全栈。但它是最后做的，不是最先做的。

## 五、代码结构与复用原则

### 5.1 目标模块结构与当前落地

下列结构和职责是目标态：Gateway 限流、Order 超时关单、Inventory Redis 预扣与对账尚未全部迁入周期 7 的微服务切片。

```
fulfillment/
├── pom.xml                      父 POM，dependencyManagement 统一版本
├── fulfillment-common/          全服务共用：统一响应、异常、枚举、常量
├── fulfillment-api/             服务间契约：Feign 接口 + DTO
│   ├── api-inventory/           库存服务对外暴露的接口与 DTO
│   └── api-payment/
├── fulfillment-gateway/         入口、全局限流
├── fulfillment-order/           下单编排、订单状态机、超时关单
├── fulfillment-inventory/       库存三态、原子扣减、Redis 预扣、对账
└── fulfillment-payment/         支付回调、幂等
```

**`fulfillment-api` 是这个结构里最值得讲的设计。** Feign 接口和 DTO 由服务提供方定义在独立模块里，调用方直接依赖这个模块就能发起调用，不需要各自重复定义一遍 DTO。

截至 2026-09-21，`microservices` 已落地 Gateway、Order、Inventory、Payment 四个进程和一个 `fulfillment-api` 契约模块。当前尚未独立拆出 `common`，Order 与 Inventory 仍使用同一个 MySQL 实例；超时关单、Redis 快速下单、对账、限流和业务看板仍保留在根目录单体。

**关键洞察：** api 模块里**只放 DTO，绝不放 entity**。entity 是数据库映射，属于服务内部实现；DTO 是对外契约。把 entity 暴露出去，就等于把库表结构变成了公开接口——以后改个字段名，所有调用方一起崩。这个区分面试常问，而且很多人答不清。

### 5.2 单个服务内的包结构

```
com.why.fulfillment.inventory
├── controller/      薄。只做参数绑定、校验、调 service、包装返回
├── service/         接口
│   └── impl/        实现。事务边界在这一层，不在 controller 也不在 mapper
├── mapper/          MyBatis 接口
├── entity/          库表映射，不出本服务
├── converter/       entity ↔ DTO 转换（MapStruct 生成）
├── config/          各类 Bean 配置
└── task/            定时任务（消息投递、库存对账）
```

**事务边界放在 service 实现层**，这是有原因的：放 controller 会让事务范围包住 HTTP 响应序列化，放 mapper 则一个方法一个事务、无法组合。另外同类内部调用 `@Transactional` 方法不生效（Spring AOP 代理走不到），这题面试问得很多，写代码时也真的会踩。

### 5.3 从单体基线演进到运行切片

周期 1 和 2 从单模块起步，周期 3 先在单体内完成业务包边界、支付幂等和 Outbox；周期 7 再形成首个跨进程运行切片。**从第一行代码开始就按未来的服务边界分包**，降低后续迁移成本，但包边界本身不等于服务边界。

所以现在的代码已经是 `com.why.fulfillment.inventory.*`，不是随手起的 `com.why.fulfillment.stock`。后续写订单和支付逻辑时同理，放进 `.order` 和 `.payment`，**不要跨包直接调用对方的 service** —— 现在跨包调用一时爽，拆分时每一处都是要改的地方。单模块阶段就用接口隔离，拆分时把接口换成 Feign 声明即可。

### 5.4 不要造的轮子

判断标准很简单：**这东西面试官会不会追问？** 不会追问的一律用现成的，写它们不长本事只耗时间。

| 你可能想自己写 | 用现成的 | 原因 |
| --- | --- | --- |
| 参数判空、格式校验 | Jakarta Validation（`@NotNull` / `@Min`）+ `@Valid` | 别在 controller 里堆 if |
| 全局异常处理 | `@RestControllerAdvice` | 一处收敛所有异常转响应 |
| entity ↔ DTO 转换 | MapStruct | 手写 get/set 几十个字段会写吐，且漏字段不报错 |
| 分布式锁 | Redisson `RLock` | 自己拿 SETNX 造锁，看门狗续期、可重入、误删别人的锁，三个坑很难全避开 |
| 延迟队列 | Redisson `RDelayedQueue` | 同上 |
| 雪花 ID | MyBatis-Plus `@TableId(type = ASSIGN_ID)` 或 Hutool `IdUtil` | 时钟回拨处理很烦，且不是本项目考点 |
| 分页 | MyBatis-Plus `PaginationInnerInterceptor` | |
| JSON | Jackson（Spring Boot 自带） | 别额外引 fastjson |
| 字符串/集合工具 | Hutool 或 Spring 的 `StringUtils` | 别写 `MyStringUtils` |
| 连接池 | HikariCP（Spring Boot 默认） | |
| 失败重试 | Spring Retry `@Retryable` | |
| 线程池 | 配 `ThreadPoolTaskExecutor` Bean | 业务代码里别 `new Thread` |
| 本地缓存 | Caffeine | |
| 指标埋点 | Micrometer | |

### 5.5 必须自己造的轮子

反过来，有几样东西**恰恰不能用现成的**，因为它们就是这个项目的全部价值所在：

原子扣减 SQL、多 SKU 排序加锁、Redis 预扣的 Lua 脚本、令牌桶限流的 Lua 脚本、本地消息表的投递与重试、支付回调的幂等判定、库存对账任务。

这几样加起来一百多行，但每一行都对应第二节里的一条「关键洞察」。**用 Sentinel 就没有限流可讲了，用 MQ 事务消息就没有一致性可讲了**——组件替你解决了问题，同时也替你拿走了讲它的资格。

这就是"不要造轮子"这句话的边界：**基础设施不造，核心机制必须造。**

### 5.6 common 模块的反模式

`common` 最容易变成垃圾桶——什么东西不知道放哪就往里塞，最后所有服务都依赖一个巨大的公共包，改一行全量重新编译，微服务拆了等于没拆。

定一条硬规则：**只有三个以上服务都要用的东西才进 common，两个服务用的就重复一份。** 过早抽象的代价比重复代码高得多，因为抽象错了要改所有调用方，重复只需要改两处。

具体进 common 的东西很有限：统一响应包装 `R<T>`、业务异常基类、全局异常处理器、状态枚举（订单状态、锁定状态）、错误码常量。就这些。

### 5.7 哪些结构可以直接借鉴 mall4cloud

**结构惯例可以照着组织，代码不拷贝。** 这两件事不一样，前者不受 AGPL 约束——分层怎么分、模块怎么切本来就是行业通行做法，不构成著作权意义上的复制。

具体可以看它的：模块划分方式（它也有独立的 `mall4cloud-api` 层）、`ServerResponseEntity` 这类统一响应的组织方式、异常体系的层次、`sku_stock` 与 `sku_stock_lock` 的表结构设计。

看完照着自己的需要组织，然后按对照式实现的规矩，把"我为什么这么分、它为什么那么分"记进 `NOTES-对照记录.md`。

### 5.8 依赖管理

父 POM 里用 `dependencyManagement` 统一所有版本，子模块引依赖**不写版本号**。Spring Boot 的 `spring-boot-dependencies` 和 Spring Cloud Alibaba 的 BOM 都通过 `<scope>import</scope>` 引入。

这样做的收益在升级时才体现：改一处版本，全部模块跟着变。子模块各写各的版本，迟早会出现同一个 jar 在不同模块是不同版本，然后报一个和版本毫无关系的 `NoSuchMethodError`。

## 六、关于你的开发方式：vibecoding + agent 面试官

这个组合能成立，但有一个前提条件，说清楚比较好。

**vibecoding 的适用边界。** 脚手架、配置、DTO、CRUD、前端页面、测试数据构造——这些代都行，写它们不长本事。但**第二节里每个功能的"关键洞察"那部分，自己写**。那不到一百行代码，恰好是全部六个失效模式的修复点，也恰好是面试追问的全部落点。代生成的那部分你能读懂、能改、能解释就够；关键洞察那部分你要能**在白纸上重新写出来**。

**agent 面试官的盲区。** 它只会问你代码里有的东西。真实面试官会问代码里没有的——"QPS 再涨十倍你怎么办"、"这个方案在多机房部署下还成立吗"、"如果不让你用 Redis 呢"。所以每轮盘问结束后，让它额外出 2 到 3 道**超出当前实现范围**的延伸题。这类题答不上来不丢人，但连想都没想过就会在真实面试里卡住。

**两条规则。** 一是盘问时不许看代码，答不上来的记下来，回去补，第二天重问一遍。二是每个周期跑完盘问才算结束——**跑通不算完成，讲得清才算完成**。

**一个提醒。** vibecode 出来的代码，读一遍觉得"懂了"和真的懂了之间差距很大。最简单的自检：把某个类删掉，凭理解重写一遍，再和原来的 diff。差异大的地方就是你以为懂了其实没懂的地方。这跟我们之前定的对照式实现是同一个方法，只是对照对象从 mall4cloud 换成了你自己生成的代码。

## 七、周期划分

每个周期是一个完整闭环：**实现 → 验证出数字 → agent 盘问 → 补洞**。每个周期结束都应该是可以停下、可以写进简历的状态。

### 周期 0：环境与骨架（3–5 天）

跑通 Docker Compose 三容器，Spring Boot 连上 MySQL 和 Redis，理解依赖注入、事务注解、MyBatis-Plus 映射。目标是建立手感，不产出数字。

你目前工作区没有任何 Java 工程，这一步别跳。跳过的代价是下一周同时卡在业务设计和框架报错上。

**已搭好：** `D:\vibecoding\fulfillment-service` 里的 compose、建表 SQL、pom、配置、实体、启动类。

### 周期 1：超卖与原子扣减

先不拆微服务，单模块把库存扣减跑通。实现「先查后扣」和「原子 SQL」两个版本，用同一个 CountDownLatch 测试分别打，记录两组超卖件数。

## 八、规模天花板与扩展路径

这一节不需要实现，但**必须讲得出来**。它回答的是面试官最爱问的那句："这套东西能扛多少？再涨十倍怎么办？"

### 先把两个数字分开

**系统总 QPS** 和**单个热点 SKU 的扣减 TPS** 是两回事，混为一谈是常见的致命错误。

前者可以很大。天猫双 11 2019 年订单创建峰值 54.4 万笔/秒，后续年份同一量级——但那是全平台、几千个节点、库存早已分桶分库、单元化部署的结果，不是某一个库存服务的数字，更不是单机数字。国内多数公司的真实大促峰值在几千 QPS 量级。

后者有硬上限。

### 单行为什么快不起来

InnoDB 对同一行的更新必须串行：行锁从 `UPDATE` 开始持有，直到事务提交才释放；提交要等 redo log 和 binlog 落盘。即便 fsync 只要 0.2 毫秒，单行的理论吞吐也就在每秒几千次。

**这不是工程没做好，是物理限制。** 把 SQL 写得再漂亮、把连接池调得再大，都突破不了它——因为瓶颈不在 CPU 也不在网络，在同一行上的串行等待。

所以问题的正确形式不是"怎么让单行更快"，而是"**怎么让请求不都落在同一行**"。

### 企业级的突破手段

**库存分桶**（最核心）。把一个 SKU 的 1000 件拆成 10 行各 100 件，请求按用户 ID 哈希落到不同桶。单行限制立刻乘以 10。代价是某个桶空了而别的桶还有货，需要桶间流转、失败重试、以及最终的合并对账。**百万级是这么堆出来的，不是靠单行 UPDATE 更快。**

**分库分表**。订单表按用户或订单号分片，把写压力摊到多个实例。代价是跨片查询和分布式 ID。

**异步化削峰**。下单只写消息队列，同步返回"排队中"，真正扣减异步执行。秒杀场景普遍这么做，用户看到的"正在抢购"就是它。代价是用户体验从"立即确定"变成"稍后确定"。

**多级缓存**。本地缓存挡住大部分读，Redis 挡住大部分写前判断，真正落到 MySQL 的只剩有效请求。这个项目的周期 5 做的就是这一层的简化版。

**内核层优化**。阿里对 MySQL 做过热点行更新优化（把同一行的并发更新在存储引擎层合并提交），这类改造需要自研分支，不在应用层的讨论范围内，知道有这回事即可。

### 本项目为什么不做这些

分桶要真实的多机压测才验证得出收益，单机上做分桶只是把一行锁变成十行锁、总吞吐受限于同一个 CPU 和同一次 fsync，数字不会好看，结论也不成立。分库分表同理。

**硬写进简历的风险远大于收益。** 写了分库分表，第一个追问就是"分了几片、路由键怎么选、跨片查询和分布式事务怎么处理"，答不上来比没写更糟。

### 面试时正确的讲法

讲天花板和路径，不讲假数字。

一个好的回答长这样："我单机压到 [实测值] QPS，继续加压 P99 就开始陡增，瓶颈在热点行的锁等待——同一行的更新只能串行，受限于锁持有时间和提交落盘。要再上一个量级，应用层已经没什么可做的了，得做库存分桶把请求打散到多行，代价是要处理桶不均和桶间流转。这部分我没有实现，因为单机环境验证不出收益。"

这个回答里没有一个大数字，但它同时证明了三件事：你知道自己数字的上限，你知道上限的成因，你知道越过去的路径。**这比任何一个漂亮数字都有说服力。**

反过来，一个学生声称在笔记本上跑出百万 QPS，面试官的第一反应不是"厉害"，是"他不知道自己在说什么"，接下来的追问就从交流变成了质证。**校招场景里，数字大不加分，数字不合理直接出局。**

### 你的数字该怎么定位

这个项目产出的全部是**对比数字**，不是**容量数字**。

"先查后扣超卖 X 件 → 原子 SQL 归零"证明的是正确性，和规模无关。"纯 DB 扣减 X QPS → Redis 预扣 Y QPS"证明的是优化有效，价值在倍数和原因，不在绝对值。简历上"（单机同环境对比）"那个括号就是在说这件事，务必保留。

## 九、让数字站得住的五个要求

这一节决定简历可信度，压测前回来再读一遍。

一是**固定并记录环境**：CPU、内存、JVM 堆与 GC 参数、数据库连接池大小、Redis 配置。改造前后必须完全一致，否则对比无意义。二是**预热**，JIT 和连接池需要热身，首轮数据丢弃。三是**多轮取中位数**，至少三轮，记录波动范围，不要只报最好的一次。四是**同时记录错误率**，QPS 上去了但错误率也上去了，那不是优化。五是**主动说明局限**。

第五条最重要。面试官在意的是你知不知道自己数字的边界，而不是数字多漂亮。

另外，`application.yml` 里 MyBatis 的 SQL 日志压测前一定要关掉，日志 IO 会让性能数字整个失真。
