## 0. 总体结论

这份设计的**骨架是对的**，而且比多数同类文档诚实。最终一致性的心智模型（§19「事实先落库，事件可重试，消费幂等，失败可补偿，长期差异可对账」）、拒绝跨服务 `@Transactional`、拒绝声称 exactly-once、把分布式锁降级为最后手段（§18）、以及用模块化单体承载 user/product/cart 而不是拆三个进程（§6.2）——这几条判断的质量高于文档的平均水平，也高于很多线上系统的实际规范。

真正的问题不在架构方向，在三个地方：

**第一，数据层的设计深度明显落后于流程层的设计深度。** §10 到 §21 的状态机、幂等、补偿写得很细，但 §22 的表设计只是把字段名列了出来——没有索引、没有唯一键标注、没有字段类型、没有 Payment DB、漏了异步命令表、`sku_stock` 缺 §11 明确定义的 `sold` 态。流程设计得再细，最后都要落在这些表上；表设计粗一格，前面所有的条件更新、租约抢占、对账公式都会在这一格里打折。**这是本次评审影响面最大的一类问题。**

**第二，存在五处口径分歧，都集中在"谁拥有哪份数据"上。** 最硬的一处是真冲突：`payment_order` 在 §6 架构图、§6.3、§12 三处都归 Payment 自有库，却在 §22 被放进 Order DB，而 §22 根本没有 Payment DB 这一节。其余四处是"未指定"或"定义写在了别处"——严重性低一档，但同样会让两个实现者读出两种结论。这类分歧落在跨服务边界和 schema 上，是最难改的位置。

**第三，"企业生产级"的判定标准本身没有写。** §2 把完成标准定义为"请求能否正确结束、失败能否恢复"，方向对，但整份文档没有任何一个量化目标：没有 SLO、没有容量假设、没有 RPO/RTO、没有故障收敛时间上限。同时限流在 V2 的任务拆分（§29）里完全消失了——一个自称"高并发电商平台"的设计，P0/P1/P2 三级任务里一条限流都没有。降级、回滚、数据归档、事件版本化同样整章缺失。这些不是细节，是"生产级"和"能跑通"的分界线。

按优先级，建议的动作顺序是：先花半天把第 2 章的五处口径冲突定死并回写文档 → 再补第 3 章里 3.1 / 3.2 / 3.4 / 3.5 这四条（都会导致返工的） → 然后把第 4 章缺的章节补成文档，不必立刻实现 → 第 5 章是论证问题，改文字即可。

## 1. 先说站得住的部分

这些不需要改，但值得知道为什么对，因为后续任何改动都不该破坏它们。

**§3 的非目标清单是整份文档最有价值的一节。** 明确写出不做优惠券、不做多商户、不做物流售后、不对接真实支付、不做分库分表和 K8s，并加上一句"不能在 V2 中创建没有实现价值的空模块"。大部分自研项目死在这一步——不断加模块，每个都只有 CRUD。这份清单把边界钉死了。

**§19 的一致性分界写法是正确的工程表达。** 把强一致边界（同库同事务）和最终一致边界（跨服务、跨存储、跨进程）分开列举，而不是笼统说"用最终一致性"。尤其"Inventory 本地事务中的库存主表、锁定记录、取消栅栏和账本状态"这一条——把栅栏和账本纳入同一本地事务，是避免"栅栏写了但账本没写"这类半状态的关键，文档写对了。

**§18 最后一条"不把分布式锁作为所有问题的默认方案"。** 先用唯一键、条件更新、确定的锁顺序，确有跨资源临界区才上 Redisson 并定义租约和故障释放——这个优先级顺序是对的，而且顺序写反是校招项目里最常见的错误（上来就 `RLock` 包住整个下单）。

**§6.2 拒绝把 user/product/cart 拆成三个服务。** 理由文档写的是"规模有限"，其实有更强的理由（见 5.3），但结论正确。反过度微服务化的判断，比多拆两个服务更能说明架构能力。

**§21 关于 Redis 的定位：MySQL 是最终事实，Redis 写入都要有过期、回补、重建或对账策略。** 以及 §11「Redis 预扣不是最终库存事实」。这条守住了，整个 Redis 快速路径才有意义；守不住就是一个会丢数据的缓存。

**§28 阶段 0「不在迁移中删除证据」、§22「不能直接删除旧表」、AGENTS.md §13「不直接修改已提交历史迁移」。** 这三条是迁移纪律，写得比设计本身更难得。

## 2. P0：口径分歧，必须先定下来

严格说只有 2.1 是两处原文互斥；2.2 / 2.3 / 2.5 是**口径未指定**——文档在 A 处这么用、在 B 处那么用，但没有任何一处给出定义；2.4 是同一件事分散在两节、就近读会读错。共同点是：不定下来就往下写，分歧会落在服务边界和数据库 schema 上，是最贵的返工。

### 2.1 支付数据无处安放（真冲突）

四处原文，三处支持 Payment 拥有自己的库：

- §6 架构图（第 126 行）：`payment-service -> Payment DB + Order API`。
- §6.3 数据所有权表：`payment` 的事实数据是"支付单、回调记录、支付状态"，访问范围是"自有数据库"。
- §12 支付模型：新增 `payment_order` 和 `payment_callback_record`，并明确"Payment 不直接修改 Order 或 Inventory 数据库"。

只有 §22 表设计反着来：`payment_order` 被列在 **Order DB** 下；**`payment_callback_record` 没有出现在任何一个 DB 里**；**整节没有 Payment DB 小节**。

所以修正方向是确定的——§22 错了，按前三处改。（附带说明：§22 的写法恰好和现状一致，`docs/project-function-boundary.md` §3 写的是 payment-service "不访问数据库"，这很可能就是 §22 漏写的原因：写表设计时照着现状抄，而没有照着自己在 §6/§12 定的目标抄。）

**建议在 §22 补一节 Payment DB：**

```text
payment_order(id, payment_no, order_id, user_id, amount, status,
              out_trade_no, channel, expire_time, create_time, update_time)
payment_callback_record(id, out_trade_no, payment_no, raw_digest,
                        signature_valid, process_status, last_error, create_time)
```

同时在 Order DB 的 `sales_order` 上保留 `out_trade_no` 和 `paid_time` 作为**冗余判定字段**（不是事实来源），用于 Order 侧独立做支付幂等而不必回查 Payment。要在文档里写明这是有意的冗余以及谁是事实方，否则下一个人会把它当成事实并去做双写一致性。

顺带一个真实决策：Payment 有了自己的库之后，它就不再是"薄服务"了，§6.1 说"Payment 保持薄服务便于替换模拟支付"的论证需要同步修改——有独立支付单状态的 Payment 不薄，但依然可替换，因为替换的是渠道适配层而不是支付单模型。

### 2.2 `PENDING_COMPENSATION` 和 `FAILED` 混用了两个状态维度

§10 定义了两条独立的状态轴：订单主状态（`CREATING → PENDING_PAYMENT`，再分岔到 `PAID → COMPLETED` 或 `CANCELED`）和库存预占状态（`RESERVING → RESERVED/FAILED`，以及 `RELEASE_PENDING`、`CONFIRM_PENDING`）。§22 的 `sales_order` 也确实开了 `status` 和 `reservation_status` 两列，说明设计者心里是分开的。

但接着：

- §10 正文："远程调用结果未知时使用 `PENDING_COMPENSATION`" —— 没说是哪一列。
- §13 时序图：`O->>DB: FAILED`、`O->>DB: PENDING_COMPENSATION` —— 也没标列。而 `FAILED` 只存在于预占状态轴，`PENDING_COMPENSATION` 两条轴上都没有定义。
- 于是"库存不足返回 409"时，订单主状态到底是什么？是留在 `CREATING`，还是需要一个主状态轴上的终态？文档没答。

这会直接导致两个实际问题：一是订单查询接口和前端拿到的 `status` 字段语义不确定；二是超时关单扫描（§15）的 WHERE 条件写不出来——它要按 `status='PENDING_PAYMENT' AND reservation_status='RESERVED'` 过滤，但如果实现者把 `PENDING_COMPENSATION` 写进了 `status` 列，这些订单就永远扫不到。

**建议在 §10 明确两件事。** 第一，`PENDING_COMPENSATION` / `COMPENSATED` 属于 `reservation_status` 轴，主状态轴不引入这两个值。第二，补全主状态轴的失败终态——库存不足或补偿确认失败时，主状态从 `CREATING` 进入 `CLOSED`（或复用 `CANCELED` 并用 `close_reason` 区分），不要让订单停在 `CREATING`（见 3.1）。然后把 §13 时序图里的状态标注改成 `status=X / reservation_status=Y` 的形式，一眼可辨。

### 2.3 购物车的事实存储没定

三处表述指向三个不同的答案：

- §7 Cart："购物车可用 Redis 保存热数据，**必要时异步持久化**" —— 倾向 Redis 为主、异步落库。
- §9："Redis Key 使用 `cart:{userId}`，Hash 或 JSON 结构保存"，以及"Redis 故障时，购物车可以返回可重试错误**或**降级为空"。
- §22 Commerce DB：`cart_item(id, user_id, sku_id, quantity, selected, create_time, update_time)` —— 一张完整的购物车表，看起来像事实存储。

"必要时异步持久化"里的"必要时"是谁判断的、`cart_item` 是事实还是副本、谁负责一致——都没写。而这两个方向的故障行为完全相反：如果 MySQL 是事实，Redis 故障时应该**回源查 MySQL**，功能完全不降级；"降级为空"意味着用户的购物车凭空清零，在真实产品里是事故级体验问题。

**两个方案都可以，但必须选一个并写进文档：**

| | 方案 A：MySQL 为事实，Redis 只读缓存 | 方案 B：Redis 为事实，异步落库 |
|---|---|---|
| 写路径 | 写 MySQL，删 Redis key | 写 Redis，投 Outbox 异步落 MySQL |
| Redis 故障 | 直接回源 MySQL，功能不降级只变慢 | 购物车不可用，需要明确的错误码 |
| 一致性 | 天然一致（cache-aside） | 最终一致，需要对账 |
| 适合 | 本项目（购物车写频率远低于库存） | 购物车 QPS 极高、允许丢失的场景 |

**推荐方案 A。** 购物车的写入频率比库存低两个数量级，没有任何理由为它引入一套新的最终一致性链路——本项目已经有三条最终一致链路（Outbox、Redis 预扣账本、异步订单命令）要维护，第四条的边际价值是负的。选 A 之后，§9 的"降级为空"这句要删掉，改成"Redis 不可用时回源 MySQL，仅吞吐下降"。

### 2.4 `sold` 态的落库方式分散在两节，就近读会读错（降级：不是冲突，是表述问题）

§11 的业务模型写了三态 `available / locked / sold`，并写"支付成功：locked → sold"。§22 的 `sku_stock(sku_id, spu_id, stock, lock_stock, version, update_time)` 里没有 `sold` 列。

单看这两节像是模型与存储分裂，但 **§7 Inventory 其实已经回答了**："Inventory 维护可售、锁定和已确认消耗三种业务含义，**实际落库继续使用当前 stock、lock_stock 与锁定记录模型**。"所以设计口径是清楚的——`sold` 是派生量，由 `sku_stock_lock` 中 `CONFIRMED` 记录聚合而来，不落主表。这一条**不构成自相矛盾**，问题只是：定义写在 §7，而会去查 `sold` 怎么存的人一定是在读 §11 和 §22。

**最小修改是就近重申**：在 §11 三态图下面加一句"`sold` 为派生量，见 §7"，在 §22 的 `sku_stock` 后附上聚合 SQL。

**但更值得考虑的是加一列 `sold_stock`**，在 confirm 的同一条件更新里维护：

```sql
UPDATE sku_stock
   SET lock_stock = lock_stock - #{count},
       sold_stock = sold_stock + #{count}
 WHERE sku_id = #{skuId} AND lock_stock >= #{count}
```

理由不是"模型要对齐存储"，而是**它能换来一条可断言的不变量**：`stock + lock_stock + sold_stock` 恒等于初始总量。有了这一列，对账从"比对两个数"变成"校验一个守恒式"，超卖、漏释放、重复确认三类问题会在同一个断言下暴露；没有这一列，你只能靠聚合 `sku_stock_lock` 来算，而那张表按 4.4 是要归档的——归档之后守恒式就断了。这是一个用一列冗余换一条不变量的交易，在库存系统里通常划算。

### 2.5 §22 的表清单不完整

漏掉的不只是 Payment DB。按 §11、§19 和现状描述，Order 侧还有一张**异步订单命令表**（现状叫 `microservice_order_command`），承担 Redis 快速路径"先持久化命令，再异步落库"的全部事实——§13 结尾那句"对于 Redis 快速路径，命令先持久化"依赖的就是它。这张表有租约、重试、退避、死信、载荷签名，复杂度不低于 Outbox，但 §22 完全没有它。

Inventory 侧的 `inventory_redis_reservation` 列出来了，但 Commerce DB 里没有登录态/会话相关的任何存储（§7 说"认证可使用 JWT 或服务端 Session"，若选 Session 就需要存储，文档没跟进）。

**建议 §22 补全成"每个服务的完整表清单"**，并在每张表后标注唯一键、主要索引和数据生命周期（见 4.4）。表清单不完整的直接后果是迁移脚本会漏，而迁移漏一张表通常要到联调才发现。

## 3. P1：设计成立但有洞，真实运行会暴露

### 3.1 `CREATING` 状态没有回收路径

§13 选择了"先持久化订单意图，再调用库存"，这个顺序是对的——结果未知时有订单事实可恢复。但代价是引入了一个中间态，而 §10 的状态机只给了 `CREATING → PENDING_PAYMENT` 一条出边。

失效场景很具体：订单写入 `CREATING` 并提交后、调用 Inventory 之前，order-service 进程被杀。这张订单没有任何后续推进者——§15 的超时扫描条件是 `PENDING_PAYMENT + RESERVED + expire_time <= now`，扫不到 `CREATING`；补偿任务（§24）的前提是"只处理明确的待补偿状态"，`CREATING` 不是待补偿状态。结果是一张永久悬挂的订单，而它可能已经、也可能没有在 Inventory 侧产生预占。

**建议补一条独立的恢复规则：** 扫描 `status='CREATING' AND create_time <= now - T`（T 取远大于 Feign 读超时的值，比如 30 秒），对每一单**先用 `orderId` 查询 Inventory 的预占结果**（§17 已经规定库存预占幂等键是 `orderId + skuId`，所以这个查询是安全且确定的），再决定推进到 `PENDING_PAYMENT + RESERVED` 还是 `CLOSED + FAILED`。关键是顺序：**先查再判，不能直接判失败**——直接判失败会漏掉"预占其实成功了"的情况，那就是库存泄漏。

顺带：这条规则要求 Inventory 提供一个"按 orderId 查预占状态"的内部查询接口，§23 的内部库存接口清单里目前只有 `GET /internal/inventory/query/{skuId}`（按 SKU 查），没有按订单查的。需要补。

### 3.2 幂等记录过期等于允许重复下单

§17 结尾："幂等记录必须有保存期限或清理策略。"这句话本身对，但没有给口径，而这里的口径是有钱的含义的。

如果 `idempotency_record` 的保留期是 24 小时，那么第 25 小时用同一个 `Idempotency-Key` 重放，会创建第二张订单、第二次预占。客户端侧重试通常不会跨 24 小时，所以这不是主要风险；真正的风险是**对账和纠纷场景**——用户说"我只下了一单为什么扣了两次"，而你已经把判定依据删了。

**建议写死两条规则。** 第一，幂等记录的清理条件不是"按时间"，而是"关联订单已进入终态 **且** 终态时间早于 T"（T 建议 ≥ 7 天，与业务纠纷窗口对齐）；未终态的订单，其幂等记录永不删除。第二，清理用软删或归档表，不要物理删——归档表的成本是几乎为零的，而"我删了所以查不到"在事后是没法交代的。

另外一个结构性选择：§22 同时在 `sales_order` 上放了 `idempotency_key` 和 `request_digest`，又单独建了 `idempotency_record` 表，**两份事实**。这会引入"订单建了但幂等记录没建"或反之的半状态（即使同事务也会在迁移、补数、手工修复时错开）。

单独的 `idempotency_record` 表适合"请求先于资源存在"的场景（比如需要先占位再慢慢创建）。本项目订单是同事务创建的，订单本身就是幂等结果，**建议只保留 `sales_order` 上的 `UNIQUE(user_id, idempotency_key)`，删掉 `idempotency_record` 表**，判定逻辑变成：插入冲突 → 读出既有订单 → 比对 `request_digest` → 同则返回既有订单，异则 409。少一张表、少一处不一致、少一次写。如果坚持保留独立表，那要在文档里写明为什么以及谁是事实方。

### 3.3 "结果未知"缺客户端重试契约

§13 的 unknown 分支返回 `202/503 可重试`。问题是**没有定义客户端应该怎么重试**。

如果客户端重试时复用同一个 `Idempotency-Key`，一切安全——会命中唯一键，返回同一张订单。但真实前端在收到 503 之后重新发起请求时，极容易重新生成一个 UUID（尤其是 key 在请求拦截器里生成的时候）。此时第二次请求创建第二张订单、发起第二次预占，而第一张订单的补偿可能还在进行中。用户看到两张待支付订单，库存被占两份。

**建议在 §13 和 §23 同时补上客户端契约，并且用响应体强制它：** unknown 分支的响应必须返回 `orderId` 和原始 `idempotencyKey`，并明确规定"客户端重试必须携带同一个 `Idempotency-Key`；若无法保证，应改为轮询 `GET /api/orders/{orderId}` 而不是重发创建请求"。同时把这条写进前端约定（§2 目标第 9 条说"前端不承载交易一致性逻辑"，但"用同一个 key 重试"不是一致性逻辑，是协议纪律，前端必须遵守）。

补充一句：`202` 和 `503` 混用在同一个分支是不合适的。`202` 表示"已受理，请轮询"（有 orderId，后台会推进）；`503` 表示"我没受理，请重试"（无 orderId）。这两种对客户端的指令完全相反，不能由同一个分支随机返回。建议 unknown 一律返回 `202` + orderId，因为按 §13 的设计订单意图已经落库了——它确实已受理。

### 3.4 Outbox 缺跨服务稳定的事件 ID

§17 幂等表写 Outbox 消费的幂等键是 `eventId/orderId`。但 §22 的 `order_outbox_event(id, event_type, biz_key, payload, status, retry_count, next_retry_time, lease_owner, lease_until, last_error)` 里**没有 `event_id` 列**，只有自增主键 `id`。

自增 id 不能当跨服务幂等键：它不在 payload 里、不稳定（迁移/重建会变）、且消费方无法据此去重。用 `orderId` 去重则会把"同一订单的不同事件"误判为重复（一张订单会产生 `OrderCreated`、`PaymentConfirmed`、`OrderCanceled` 多个事件）。

**建议给 `order_outbox_event` 加 `event_id CHAR(36) NOT NULL UNIQUE`（应用侧生成 UUID），并把它写进 payload 和消息头。** 消费端的去重表以 `event_id` 为主键。同时 `UNIQUE(event_type, biz_key)` 视事件语义决定加不加——对 `PaymentConfirmed` 这种一单一次的事件，加上这个唯一键可以在生产侧就挡住重复写入，是很便宜的保险。

### 3.5 §22 全节没有索引、唯一键和扫描方式设计

这是整份文档最系统性的缺口。§22 只列了字段名，没有一处索引、一处唯一键标注、一处字段类型（除了 §8 提到价格用 `DECIMAL(12,2)`）。

而这份设计里有**五个扫描型任务**：超时关单扫描、Outbox 发布扫描、异步命令领取扫描、补偿重试扫描、对账扫描。每一个都是"按状态 + 时间过滤，取一批，条件更新抢占"的模式。没有 `(status, next_retry_time)` 这类复合索引，它们全是全表扫描；数据量到十万级就会开始拖垮实例，而这恰恰是"高并发"项目最不该出问题的地方。

**建议 §22 每张表补三项：主要索引、唯一键、扫描方式。** 至少这些是确定要的：

```text
sales_order          UNIQUE(user_id, idempotency_key)
                     KEY(status, reservation_status, expire_time)   -- 关单扫描
                     KEY(user_id, create_time)                      -- 订单列表
order_outbox_event   UNIQUE(event_id)
                     KEY(status, next_retry_time, id)               -- 发布扫描
sku_stock_lock       UNIQUE(order_id, sku_id)                       -- 预占幂等的根
                     KEY(sku_id, status)                            -- 按 SKU 聚合/对账
inventory_reservation_fence  PRIMARY KEY(order_id)
inventory_redis_reservation  UNIQUE(order_id)
                     KEY(status, create_time)                       -- 账本物化扫描
cart_item            UNIQUE(user_id, sku_id)
payment_order        UNIQUE(out_trade_no)
                     KEY(order_id)                                  -- 见 3.8
```

另外扫描方式要写明用**游标分页**（`WHERE ... AND id > :lastId ORDER BY id LIMIT :n`）而不是 `OFFSET`——`OFFSET` 在深翻页时是 O(n)，且抢占场景下每轮的结果集都在变，`OFFSET` 会漏行。这类细节写不写，决定了这套调度器在 1 万行和 100 万行时是不是同一个东西。

### 3.6 Redis Cluster 下多 SKU 原子预扣不成立，§21 的迁移方案只对了一半

§21 写："Redis Lua 多键脚本当前面向单实例；迁移 Cluster 时必须通过 hash tag 保证同一订单相关键在同一槽，**或重新设计脚本和补偿流程**。"

按订单打 hash tag，对**订单作用域的键**（幂等标记 `mark:{order123}`、取消墓碑 `tomb:{order123}`、预扣账本键）是成立的。但对**库存键**不成立，而库存键才是预扣脚本的核心：库存必须是「一个 SKU 一个键」，否则同一 SKU 在不同订单下会变成不同的键，库存就分裂了。既然库存键必须按 SKU 命名，它的槽位就由 SKU 决定；一个订单包含任意几个 SKU，无法保证它们落在同一槽。**结论是：Redis Cluster 下，跨多个 SKU 的单次原子 Lua 预扣在原理上做不到。**

文档那句话的后半句"或重新设计脚本和补偿流程"其实已经指向了正确方向，只是没有展开。三条出路，应该在文档里明确选一条：

其一，**所有库存键共用一个固定 hash tag**（如 `stock:{inv}:sku_10086`）。多 SKU 原子性保住了，代价是全部库存落在一个槽、一个主节点上——分片对库存无效，库存吞吐等于单节点吞吐。对本项目这是最实际的选择，因为库存本来就是热点集中的。

其二，**放弃跨 SKU 原子性**，改为按 `skuId` 升序逐个预扣，任一失败则反向回滚已扣的部分。这是分布式版本的两阶段，需要补偿路径且中间态可见（别的请求可能看到部分扣减），复杂度显著上升。

其三，**库存 Redis 独立部署为单实例/主从，不进 Cluster**，业务其余部分（购物车、缓存、限流）用 Cluster。这是最干净的架构切分，推荐作为默认答案。

不管选哪条，§21 前半句"通过 hash tag 保证同一订单相关键在同一槽"建议限定成"仅适用于订单作用域的键；库存键的分槽问题见上"，否则读者容易以为换个 key 命名就能整体上 Cluster。

### 3.7 关单的多实例抢占，你已经有正解但写成了租约

§15 里有一句写得很准："支付和关单竞争同一订单条件更新。支付先成功时，关单更新影响行数为 0。"这句话其实已经给出了多实例关单的完整答案——**条件更新本身就是抢占器**。两个实例扫到同一批订单毫无问题，因为只有一个能把 `status` 从 `PENDING_PAYMENT` 改成 `CANCELED`，另一个拿到 0 行然后跳过。不需要租约，不需要分片，不需要选主。

但 §18 对"多实例任务"只给了一条路径："数据库租约或消息消费组抢占，租约过期可恢复"——没有按任务类型区分。对 Outbox 发布和异步命令领取，租约是必要的（因为"处理中"是一个耗时且不可重复的外部动作）；对关单，租约是纯粹的多余复杂度，而 §15 自己已经给出了更简单的答案。

**建议 §18 把这两类任务分开表述：**

| 任务类型 | 抢占机制 | 理由 |
|---|---|---|
| 状态推进型（关单、取消、确认） | 目标行的条件更新，`affected rows` 定胜负 | 推进动作本身就是原子的，重复扫描无害 |
| 外部动作型（Outbox 投递、异步落库、补偿调用） | 行级租约 + 过期重认领 | 外部调用耗时且不可重复执行，需要独占窗口 |

另外 §15 的 `expire_time <= now` 没写 `now` 的时钟来源。多实例部署时容器时钟会漂移，应统一用**数据库时钟**（`expire_time <= NOW()`），不要用应用侧 `LocalDateTime.now()` 传参。这是一行代码的差别，但在多实例下是"提前关单"事故的常见根因。

### 3.8 支付单状态缺失败分支，且"一单能否有多个支付单"没有表态

§12 的支付单状态是 `CREATED -> PAYING -> SUCCESS / CLOSED`。缺一个 `FAILED`——真实支付有余额不足、用户主动取消、渠道拒绝等明确失败，模拟支付也应该能构造这些分支，否则前端演示不出失败路径，Order 侧也收不到"这次支付失败了，但订单还能再付"的信号。`CLOSED` 语义模糊：它是"支付超时关闭"还是"支付失败"？这两者对用户可见行为不同（前者可重新发起，后者可能要换渠道）。建议拆成 `FAILED`（本次尝试失败，订单仍可支付）和 `CLOSED`（订单已关，支付单随之作废）。

更重要的是文档完全没有回答：**一张订单能不能创建多个支付单？** 这是支付设计里最经典的分叉点。用户点支付 → 页面卡住 → 返回 → 再点支付，第二次是复用第一个支付单还是新建？

如果允许多个，必须处理"两个支付单先后都回调成功"（真实世界会发生：用户在两个渠道各付了一次）——需要定义超额支付的识别和退款口径，但 §3 的非目标里明确写了不做退款。**所以本项目应该选择不允许：`payment_order` 上加 `UNIQUE(order_id)`**（或 `UNIQUE(order_id, status)` 配合只保留一条活跃支付单），创建支付单接口改为 get-or-create 语义：已有未终态支付单则返回既有的。这样"重复付款"在数据模型层面就不可能发生，不需要退款能力兜底，和 §3 的非目标自洽。这个取舍值得单独写一小段，它是设计深度的直接体现。

### 3.9 Redis 快速路径缺完整时序，而它是最复杂的路径

这条路径的**机制**文档其实写到了：§11 有一整段（"Order 先记录可恢复命令，Inventory 记录自己的 Redis 账本；订单落库后物化，明确失败终态才补偿，未知结果继续重试"），§17 给了幂等键 `orderId + payload signature` 和取消墓碑，§22 有 `inventory_redis_reservation` 及其 `PENDING/MATERIALIZED/COMPENSATED` 状态。缺的是**把它们串起来的时序**——§13 和 §14 分别给了同步下单和支付的时序图，Redis 快速路径只有 §13 末尾一句"命令先持久化，再由 Inventory 执行 Lua 预扣"。

为什么偏偏这条最需要时序图：它的状态组合数远超同步路径，而且有一个同步路径没有的窗口——**在订单尚未落库的那段时间里，超时关单扫不到它、用户查不到它、支付无从发起**。如果这段窗口里命令领取反复失败，用户看到的是"下单成功（202）但订单不存在"。这个窗口期的用户可见性和收敛上限，文档没有定义。

**建议补 §13.1「Redis 快速路径完整时序」**，至少覆盖四件事：202 之后客户端如何轮询到订单（需要在 202 响应里就返回预分配的 orderId，而不是等落库才有）；命令未落库期间的到期处理（命令表自己也要有 expire，不能只靠订单表的 `expire_time`）；Lua 预扣成功但订单最终落库失败的补偿路径与墓碑；以及这条路径下"用户可见的订单状态"有哪些。

### 3.10 Gateway 没有定义内部头剥离规则

§23 写"内部接口继续使用服务间认证；外部 Gateway 不暴露库存变更接口"。这挡住了路由，但没挡住**头部伪造**。

当前内部鉴权是共享令牌 `X-Internal-Service-Token`（AGENTS.md §8）。V2 引入用户体系后，Gateway 大概率还要向下游传 `X-User-Id` 之类的身份头。只要 Gateway 没有显式剥离入站请求里的这些头，外部客户端就可以自己带上 `X-User-Id: 1`，下游服务无法分辨它来自 Gateway 还是来自攻击者——这是越权读写别人订单的标准路径。

（说明：本次评审不核实代码，所以不断言这个洞当前是否已存在。但设计层面它一定会在 §7 的 User 模块落地时出现，而设计文档现在没有任何一处约束它。）

这个问题成本极低（Gateway 加一个 filter，把内部头列入剥离清单），不应该放到 §28 阶段 4"运行安全与高可用"。

**建议写进 §23 并列入 P0：** Gateway 必须在路由前无条件移除所有 `X-Internal-*` 和身份类请求头，再按自己的认证结果重新注入。同时下游服务不应信任任何未经 Gateway 签名的身份头——最小改动是把 `X-User-Id` 改为从内部令牌/JWT 的载荷中取，而不是从独立的头里取。

顺带回答一个会被追问但文档没写的点：支付回调用的是时间窗 + HMAC（§12 写"带时间戳和 HMAC"，五分钟的具体窗口写在 AGENTS.md §8），看起来缺 nonce 防重放。实际上**不需要 nonce**——重放攻击在这里的效果等于重复回调，而 `out_trade_no` 的唯一约束和订单条件更新已经把重复回调变成幂等操作。建议在 §12 把这个推理写出来，否则读者会以为漏了一环（这也是一个很好的"我们为什么不需要它"的论证，比加一张 nonce 表更有说服力）。

### 3.11 商品列表的库存读放大没有处理

§6.3 写 commerce "调用 Inventory 查询可售库存"，§2 目标 1 是"用户可以浏览商品和 SKU，查看价格及可售库存"。

把这两条连起来：商品列表页一页 20 个 SPU、每个 SPU 若干 SKU，渲染一次就是几十次 Inventory 查询。列表页是整个商城读 QPS 最高的入口，而 Inventory 是整个系统最不该被读打爆的服务——它要保护的是写路径的热点行。大促时列表页的读流量会直接挤掉下单的写能力，这是典型的"读把写拖死"。

**建议在 §21 明确库存读的三个档位：** 列表页用 Redis 缓存的近似可售量（秒级过期，允许不准，前端只显示"有货/紧张/无货"而不显示精确数字）；详情页用短缓存的精确值（可以不准，但要标注为展示值）；**下单时以 Inventory 的原子扣减为唯一判定，绝不信任任何缓存值**。第三条已经隐含在 §9"不能把购物车校验当成库存锁定"里；§21 也已经写了"商品详情和列表的短时缓存"——但那说的是**商品信息**的缓存，和**库存数量**的缓存是两件事。后者牵涉一个业务决策："展示的库存允许不准到什么程度"，这个决策文档没做，而它决定了 Inventory 会不会在大促时被读流量压垮。

同时 §23 的内部接口清单里应该补一个批量查询 `POST /internal/inventory/query/batch`——一次查一组 SKU。逐个 `GET /internal/inventory/query/{skuId}` 在列表场景下是 N+1，这个接口不补，上面的缓存策略也救不回来。

### 3.12 库存表里的 `spu_id` 越界了

§22 的 `sku_stock` 和 `sku_stock_lock` 都带 `spu_id`，§16 预占流程第 1 步写"校验订单号、SKU、数量和 **SPU 关系**"。

但按 §6.3，SPU/SKU 的基础信息归 commerce 所有，Inventory 只拥有"可售库存、锁定记录、Redis 预扣账本、对账"。Inventory 没有商品目录，无从判断 SKU 与 SPU 的从属关系是否正确——它只能校验"传进来的 spu_id 和我表里存的 spu_id 是否相等"，而它表里那个值也是当初由别人传进来的。这是一个**自证循环**，不构成校验。

**建议两条同时改：** §16 第 1 步删掉"SPU 关系"，Inventory 只校验订单号、SKU 存在性和数量合法性；§22 里 `sku_stock.spu_id` 要么删掉，要么在文档里标注为"Order 传入的冗余快照，仅用于排障和对账分组，Inventory 不据此做业务判定"。留着不标注是最坏的选择——下一个实现者会真的在预占路径上加一个毫无意义的判等，并且在 commerce 改了商品归属之后触发误拒。

## 4. P2：生产级规划缺的整章

前面三章说的是"写了但有问题"。这一章是"完全没写"，而且每一条都是"企业生产级"这个定语的组成部分。这些不必立刻实现，但应该作为章节写进 DESIGN_V2.md——因为它们会反过来约束前面的设计。

### 4.1 SLO 与容量假设

§25 列了一长串要采集的指标，但整份文档**没有一个目标值**。§2 把完成标准定义为定性的业务行为。这样一来，压测跑出来的数字既不能判定通过也不能判定失败，故障注入后"多久收敛算正常"也没有基准。

一份生产级设计应该给出的是"在什么条件下、什么指标、什么阈值"。建议补一节，哪怕全部是单机口径，也要写死：

```text
条件：单机 Docker Compose、MySQL 单实例、Redis 单实例、JMeter 同机施压
正确性 SLO（硬指标，不达标即失败）
  - 超卖件数 = 0
  - 已确认库存 + 锁定库存 + 可售库存 恒等于初始总量
  - 幂等重放不产生第二张订单、第二次扣减
性能 SLO（对比口径，不外推容量）
  - MySQL 同步下单 P99 < X ms @ N 并发
  - Redis 受理路径 P99 < Y ms @ N 并发
恢复 SLO
  - 任一服务 kill -9 后，未完成的预占在 T 秒内收敛（释放或确认）
  - Outbox 积压在下游恢复后 T 秒内清空
  - 对账差异持续超过 T 秒触发告警
```

其中**正确性 SLO 是本项目真正的卖点**，而它现在完全没有被表述成 SLO。性能数字在单机条件下只有对比意义（文档 §31 第 6 条已经写对了这一点），但正确性指标是可以斩钉截铁断言的——这是应该被放在最前面的东西。

### 4.2 限流在 V2 的任务拆分里消失了

§21 把"令牌桶限流"列为 Redis 的用途之一。然后：§6 架构图里没有限流，§29 的 P0/P1/P2 任务清单里**一条限流都没有**，§26 的部署清单里也没有。

对一个定位为"高并发电商平台"、并且在 §1 明确说要解决"大促和故障条件下的真实问题"的设计，这是个显眼的缺位。过载保护不是优化项，它是**可用性的前提**——没有限流，热点 SKU 的流量会把整个 Inventory 拖垮，进而拖垮下单。值得注意的是 §1 列举的八个真实问题里（超卖、死锁、重复下单、重复回调、支付与关单竞争、消息重复、Redis/MySQL 不一致、重启恢复），**一个都不是过载类问题**——这说明"高并发"在这份设计里被理解成了"并发正确性"，而不包含"并发容量与自我保护"。这两者是不同的能力，一个自称高并发平台的设计应该两者都有。

**建议补一节「限流与过载保护」**，并至少分三层写清楚：Gateway 层做全局 QPS 和单用户维度限流（保护整个系统）；Inventory 层做热点 SKU 维度限流（保护单行）；数据库连接池和 Feign 线程池做并发上限（兜底）。关键是要写明**超载时的行为**：返回 `429` 并带 `Retry-After`，**不排队**。排队会把过载转化为延迟，延迟再转化为上游超时和重试，重试再放大流量——这是雪崩的标准剧本。然后把限流放进 P1（不是 P2），因为没有它，P1 的"热点 SKU 故障注入"根本跑不出有意义的结果。

### 4.3 降级策略

§9 提了一句购物车的降级（而且是错的，见 2.3）。其余依赖全部没有降级定义：Redis 挂了下单还能不能做？MySQL 主库挂了读能不能继续？Inventory 挂了商品页还能不能展示？RabbitMQ 挂了 Outbox 怎么办？

其中最关键的一条是 **Redis 不可用时库存快速路径怎么办**。有两个合理答案，但必须选一个：自动回落到 MySQL 同步路径（可用性优先，容量下降到 §4.1 里 MySQL 路径的水平，需要一个熔断器和回落开关）；或者直接快速失败返回 503（一致性优先，避免回落后 MySQL 被打垮造成更大范围故障）。

**推荐前者，但必须配合 4.2 的限流**——否则回落瞬间全部流量涌向 MySQL，等于用一个故障换一个更大的故障。这个"降级必须和限流成对出现"的关系，是很值得单独写一段的架构判断。

### 4.4 数据生命周期与归档

Redis 侧的生命周期文档写了：§21"所有 Redis 写入都要有过期、回补、重建或对账策略"，§9"设置合理过期时间"。**MySQL 侧一条都没有**，除了 §17 那句"幂等记录必须有保存期限"。而这套设计里有**六张只增不减的表**：`order_outbox_event`、异步命令表、`sku_stock_lock`、`inventory_reservation_fence`、`inventory_redis_reservation`、`payment_callback_record`（后两张按 2.1 和 2.5 还没进 §22 的表清单，补进去时应连生命周期一起写）。

`inventory_reservation_fence` 尤其值得注意：它是每订单一行、且每次预占都要查的表。不清理的话，它会变成一张持续膨胀、且在写路径上被高频查询的表——这是设计里最先会变慢的地方。

**建议补一节，给每张表写明三件事：保留期、清理触发条件、清理方式。** 原则是：清理条件必须绑定"关联业务已终态"而不是单纯的时间；终态表归档而不是删除；清理任务本身要限速（`LIMIT` + 游标，避免一次删百万行锁表）。`sku_stock_lock` 是个例外——它是库存守恒式的一部分（见 2.4），归档它会破坏对账，应该单独说明归档后如何维持守恒断言（通常是把归档量并入 `sold_stock` 的快照）。

### 4.5 迁移没有回滚方案

§28 的五段（阶段 0 到阶段 4）全是前进路径，没有一处写"这一步失败怎么退回来"。

阶段 2 的「Order 接入 Idempotency-Key 和统一请求摘要」是个典型例子：这会改变订单创建的核心判定逻辑，上线后如果发现 digest 的规范化有 bug（字段顺序、精度、空值处理任一处不一致就会导致合法重试被判成 409），需要能在几分钟内退回去。

**建议给每个阶段补一行回滚口径**，并且把可回滚性变成 schema 变更的硬约束：所有 schema 变更必须向后兼容（只加列、只加索引、只加表），使得**回滚代码不需要回滚数据**。这条约束一旦写进文档，就会反过来禁止某些设计——比如 §22 里把 `order` 表改名为 `sales_order`，这个变更天然不可只回滚代码（见 5.4）。这正是回滚章节的价值：它会倒逼前面的设计做得更保守。

### 4.6 事件契约与版本化

§20 列了六个事件名（`OrderCreated`、`PaymentConfirmed`、`OrderCanceled`、`InventoryReserved`、`InventoryReleased`、`InventoryConfirmed`），但没有定义任何一个事件的 payload 结构、必填字段、版本策略或兼容规则。§5 第 6 条自己把"没有统一事件命名"列为当前问题之一，§28 阶段 3 和 §29 P1 也都排了任务（"统一 Outbox 事件结构"、"统一 Outbox 事件格式、租约、退避、死信和人工重放"、"明确每个事件的生产者、消费者和幂等键"）——**任务排了，但"统一成什么样"的内容一个字没有**。而这恰恰是必须在动手前定下来的那部分，否则到了阶段 3 还是要现想。

**建议给事件补一个最小契约规范：** 每个事件固定带 `eventId / eventType / version / occurredAt / bizKey / payload` 六个顶层字段；payload 内部只允许新增字段，不允许删除或改变已有字段语义；消费端必须忽略未知字段（禁止用严格反序列化）；确需破坏性变更时发新版本事件名（`PaymentConfirmed.v2`）并双写一段时间。这套规则在只有数据库 Outbox 的阶段就该建立，等接了 RabbitMQ 再补，历史消息已经没法统一了。

### 4.7 特性开关与路径切换

这套设计里并存着大量可切换的路径：MySQL 同步下单 / Redis 快速下单、单体 / 微服务、Outbox 直投 / RabbitMQ、限流开 / 关、降级开 / 关。文档对配置的全部交代是 §26 的"所有服务通过环境变量配置地址、账号、密钥和超时"，以及 §27.2 把"无服务发现和运行时切换"记为问题、解法是"V2 先保留环境变量；P2 再接注册/配置中心"——注意那一条说的是**服务地址**的运行时切换，不是业务行为开关。

环境变量的问题是**改它要重启**。而上面这些开关恰恰是故障时最需要立刻拨动的——Redis 出问题时你需要在 10 秒内关掉快速路径，而不是走一遍发布流程。把它推到"P2 接配置中心"也不对：配置中心是实现手段，而开关模型（有哪些开关、默认值是什么、拨动的后果是什么）是设计内容，现在就该定。

**建议补一小节「运行时开关」**，定义一个最小的开关模型：开关值存在配置表或 Redis、有默认值（读不到时按默认走）、变更有审计、且每个开关都要写明"拨动它会发生什么"和"什么条件下应该拨动"。不需要引入配置中心，一张表加一个本地缓存就够。这一节同时是 4.3 降级能力的落地载体——没有运行时开关，降级策略就只是一段文字。

## 5. 决策本身没错，但论证需要重写

这四条不影响实现，影响的是这份设计能不能说服人——包括半年后的你自己。

### 5.1 RabbitMQ 的价值主张写反了

§20 给的引入理由是："本项目事件量和路由复杂度有限，RabbitMQ 的确认、重试和死信更容易在本地部署和演示。"

这个论证站不住，因为**确认、重试、死信这三项能力，现有的数据库 Outbox 调度器已经全部具备**——§22 的 `retry_count / next_retry_time / lease_owner / lease_until / last_error` 就是为它们准备的字段。按这个理由，RabbitMQ 带来的是纯增量的复杂度（一个新中间件、一套新的运维、一类新的故障模式）和零增量的能力。

消息中间件相对于 Outbox 直投，真正的增量价值是另外三项：**发布方与消费方的可用性解耦**（Inventory 挂了 Order 照常发布，不需要 Order 侧的调度器持续重试并堆积）；**扇出**（一个 `PaymentConfirmed` 同时被库存确认、通知、统计三个消费者接走，Outbox 直投做不到，除非在发布器里硬编码所有下游）；**削峰**（大促时事件产生速率远高于消费速率，Broker 吸收峰值，Outbox 直投只能靠重试退避，而退避会让积压恢复变慢）。

**建议把 §20 的理由改写成这三条**，并加一句边界："在只有单一消费者且下游可用性可接受的场景下，Outbox 直投已经足够；RabbitMQ 的引入条件是出现第二个消费者或下游长时间不可用。"这样写的好处是：它同时定义了**什么时候不该引入**，而这比"为什么引入"更有说服力。

### 5.2 双路径共存没有收敛时间点

§4.3 和 §27.1 都承认存在两套实现（单体与微服务各有一套订单命令表、库存 Redis 适配、调度器、对账），§27.1 的处置是"单体标注为 regression baseline，消费者路径只走微服务"。方向正确。

但 §28–§30 的整个演进路线里，**单体从未退场**。这意味着每一次改库存状态机、Lua 脚本、对账公式、Outbox 语义，都要在两处同步。这个成本已经在 AGENTS.md 里显形了——那份文档里有大量"注意你在哪条路径上"的规则（§2 两条路径、§5 逐条区分、§19「不要用一个路径的实现假设覆盖另一条路径」）。当约束文档需要反复提醒开发者"你在哪条路径"时，说明架构债已经转移到了文档里。

**建议补一条明确的冻结条款：** 单体在 V2.1 完成后**冻结**——不再跟进任何新特性，只保留能产出对照证据的那几个实验（超卖对照、死锁对照、MySQL vs Redis 吞吐对照），其余与微服务重复的实现（Outbox、异步命令、对账、看板）删除或移入 `src/test` 作为实验夹具。冻结日期写进 §30。不写日期的"暂时保留"，最后都会变成永久保留。

### 5.3 commerce 不拆分的理由可以更强，但退出条件要量化

§6.2 的理由是"用户、商品和购物车规模有限，拆成三个服务会增加契约、部署和数据同步成本"。这是成本侧的论证，成立但偏弱——因为它会被"那等规模大了再拆不是更麻烦"这种反问顶回去。

更强的理由在能力侧：**user/product/cart 三者没有独立的并发或一致性问题**。它们是读多写少、无热点行竞争、无跨服务事务、无补偿需求的 CRUD。而 Order / Inventory / Payment 各自拥有一个独立的难题（订单状态机与幂等、热点行与死锁、外部回调与签名）。**服务边界应该切在难题的边界上，不是切在名词的边界上**——按名词切会得到一堆只有转发的服务，按难题切才能让每个服务的独立部署有意义。这句话可以直接替换 §6.2 现在的论证。

退出条件方面，§6.2 说"未来商品读流量或购物车规模达到独立部署条件时"——"条件"没有量化。建议给一个可判定的阈值，比如"商品读 QPS 达到订单写 QPS 的 10 倍以上，或 commerce 的扩容需求与 order 出现明显错配时"。可判定的退出条件，比模糊的"未来视情况"更能体现这是一个有意识的阶段性选择。

### 5.4 `order` → `sales_order` 改名的收益与成本不成比例

§22 写"现有表名 `order` 为 SQL 保留字，改名为 `sales_order` 只能通过兼容迁移并同步 Mapper，不能直接删除旧表"。纪律是对的，但这个改名本身值不值得做，文档没有论证。

收益：去掉每处 SQL 里的反引号。成本：一次不可只回滚代码的 schema 变更（违反 4.5 建议的硬约束）、全部 Mapper XML 与实体同步修改、所有历史迁移脚本与证据文档中的表名失去对应、以及迁移窗口内的双表一致性风险。

**建议要么明确放弃这次改名**（MyBatis 用反引号完全可以工作，这是纯洁癖驱动的变更），**要么把它挪到一个独立的、不与任何功能变更同批次的维护窗口**，并写明回滚方式（保留旧表 + 视图或触发器双写，验证后再删）。混在阶段 1/2 的功能迁移里做，是在给自己增加一个与业务无关的故障面。

## 6. AGENTS.md 的附带问题

不是本次评审的主体，但这两条会实际影响协作质量。

**§10 Agent Development Rules 和 §11 RAG Development Rules 应该删掉。** 这是一个电商履约项目，这两节各自以"本节默认不适用"、"当前没有 Parser、Chunker……"开头，之后给的全是"若未来引入则应如何"的条件性规则。同类内容在这份文档里还出现了两次——§5 有一小节 Agent / RAG 业务边界，§18 的功能放置表也有一行 Agent/RAG/LLM。同一个"当前不存在的东西"被写了四处。

这么写有两个坏处：占掉约束文档的注意力预算（454 行的文档，读者对每一节的重视程度是被稀释的）；以及更微妙的——它们会**诱导**联想，让 coding agent 在看到"workflow""tool"这类词时往那个方向靠。§1 第 26 行已经有一句"当前没有 Agent、RAG、LLM、向量库或 Tool Calling 子系统，不要创建对应目录"，那一句就够了，§10、§11、§5 的对应小节和 §18 的那一行全删。

**§17 把本机绝对路径写进了仓库文档：** `D:\vibecoding\.toolchains\maven\apache-maven-3.9.16\bin\mvn.cmd` 和 `D:\vibecoding\.m2\repository`。换一台机器、换一个用户名，这段命令直接失效，而它是文档里唯一的微服务测试入口。建议改为相对路径或环境变量（`$env:MAVEN_HOME`），并把绝对路径的示例移到 README 的本机配置小节。

**更一般的一条观察：** AGENTS.md 454 行 + DESIGN_V2.md 748 行 = 约 1200 行的约束与设计文档，而 commerce-service 和 frontend 这两个 V2 的主体还没开始。规则数量领先于代码数量本身不是问题，但它会放大一个风险：规则越多，"文档说 A、代码做 B"的组合就越多，而每一次不一致都会削弱整份文档的权威——一旦读者发现有几条是过时的，他对其余每一条的信任都会打折。建议把 AGENTS.md 压缩到 150 行以内，只保留**硬约束**（依赖方向、Do Not 清单、Definition of Done），把解释性、背景性、路径区分类的内容全部移入 DESIGN_V2.md 或删除。一份 150 行、每条都是禁令的 AGENTS.md，实际约束力高于 454 行有一半是背景介绍的版本。

## 7. 建议的修订顺序

先改文档，不要先改代码。前两步的产出都是 DESIGN_V2.md 的修订，成本低但会改变后续所有实现。

**第一步（半天，纯文档）：把第 2 章五处口径分歧定死。** 顺序建议：先定 payment 数据归属（2.1，影响服务边界），再定状态轴划分（2.2，影响所有 SQL 的 WHERE），再定购物车事实存储（2.3）、`sold` 的落库与就近表述（2.4）、补全表清单（2.5）。这五条互相牵连，一起定比分开定省事。

**第二步（半天，纯文档）：补第 3 章里会导致返工的四条。** 3.1 `CREATING` 回收规则（要新增一个 Inventory 内部接口，越晚补越贵）、3.2 幂等表二选一（涉及删表，越晚删越贵）、3.4 Outbox `event_id`（涉及加唯一键，有数据后加要先去重）、3.5 索引与扫描方式（涉及 schema，和上面两条一起出迁移脚本最划算）。

**第三步（一天，文档 + 少量代码）：补第 4 章缺的章节。** 优先级是 4.1 SLO（它会定义后面所有验收）→ 4.2 限流（它是 P1 故障注入的前提）→ 4.3 降级 → 4.6 事件契约。4.4 数据生命周期、4.5 回滚、4.7 开关可以稍后。这一步里唯一建议立刻写代码的是 **3.10 的 Gateway 内部头剥离**——它是一个当下就存在的越权面，改动量约二十行。

**第四步（半天，纯文字）：重写第 5 章的四处论证，删 AGENTS.md 的 §10/§11。**

**不建议现在做的：** RabbitMQ 接入（先把 5.1 的论证写清楚，再判断要不要做）、`order` 表改名（5.4）、Redis Cluster 迁移（3.6 的结论是库存不该进 Cluster，那就不需要迁）。这三件事的共同点是：投入不小，而在把前面几步做完之前，你甚至无法判断它们值不值得做。
