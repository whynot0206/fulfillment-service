本轮浏览器流程：

## 7. C01 首次失败：不同订单也可能争用空范围间隙锁

先准备 31 个合成用户和购物车，再通过真实 Commerce 订单预占 SKU 1002 的 90 件，将可售库存从 100 临时缩到 10；随后发送 30 个不同用户、不同幂等键的结算请求。没有通过业务 SQL 修改库存，也没有用同键重放代替独立竞争。

首次结果为 10 个 RESERVED、9 个 FAILED，以及 11 个因基础故障进入补偿的 COMPENSATED。客户端这三类响应均为 HTTP 200，但后者不能归类为正常售罄；脚本明确失败，停止于 C01，未执行后续两 SKU 场景。最终通过本人取消 API 收尾，库存回到本次基线：SKU 1001 可售 97、SKU 1002 可售 100，锁定和活跃锁均为 0；清理成功不抵消场景失败。

`SHOW ENGINE INNODB STATUS` 留存了不同订单插入 `sku_stock_lock` 时，`uk_order_sku` 上的 gap lock 与 insert intention 相互等待，MySQL 回滚其中事务的事实。结合当时默认 REPEATABLE READ 事务下按订单查询空锁范围再插入的代码路径，定位为新订单空范围锁竞争；不是相反 SKU 顺序造成的那类旧实验死锁。仅有最后一份死锁快照，不能据此宣称逐一证明全部 11 个异常都具有同一完整锁图。

原理参考：[MySQL 8.0 官方隔离级别说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html)。READ_COMMITTED 下锁定读通常只锁索引记录，不保护其前面的间隙；外键和重复键检查仍可能使用间隙锁，死锁也仍可能发生。因此本次判断依据是具体死锁图、调用路径与修复后复验，而不是“换隔离级别即可保证无死锁”。

局部修复已将 Inventory 的 reserve/release/confirm 本地事务调整为 READ_COMMITTED，保留订单取消栅栏、唯一键、原子库存条件更新和统一 SKU 顺序；不改全局数据库隔离级别，不靠扩大重试把基础故障算成售罄。修复后完整构建及 270 项测试通过，新包首批真实复验得到 **10 RESERVED、20 FAILED、0 基础故障**，102 条断言全部通过。未重置库存，以新用户、新幂等键独立执行并通过本人取消 API 收尾；最终可售库存恢复为 SKU 1001 的 97 件、SKU 1002 的 100 件，锁定及活跃锁均为 0，`cleanupSettled`、`proxyRestored` 均为 true。

N06/N07 首批实测持有经过 Commerce 有货检查的两 SKU 预占请求，用另一笔真实订单抢完其中一项，再及时放行。购物车输入顺序分别为 `[1001,1002]` 和 `[1002,1001]`：从目标结算发送到请求放行为 214/222 毫秒，放行控制调用完成为 216/224 毫秒，均未错过窗口。两次均核对原代理 sequence 的上游完成状态为 REJECTED；目标订单为 CANCELED/FAILED、全部库存锁行数为 0，足量 SKU 库存未减少，不是请求超时后的补偿冒充事务拒绝。相反购物车输入顺序只验证归一化后的业务结果，不等于反向数据库加锁或重新复现旧死锁实验。

第二独立批次使用另一组新用户与幂等键，未重置库存，再次得到 10 成功、20 业务拒绝、0 基础故障。两 SKU 放行请求为 218/227 毫秒、控制调用完成为 220/229 毫秒；原请求均实际完成并被拒绝，目标订单全部锁行仍为 0。取消后同样恢复可售 97/100、0 锁，清理和代理恢复标记均为 true。本批 103 条断言相较首批 102 条多一条夹具购物车删除检查，来自竞争结果后准备动作的差异，不是额外业务场景。

这只证明当前单实例、有限规模的两批独立复验通过，不是“消除所有死锁”或生产容量结论。局部事务隔离调整后的故障/安全回归已单独留证，不能把两批统计外推为任意并发规模。
