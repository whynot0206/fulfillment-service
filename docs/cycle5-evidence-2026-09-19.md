# 周期 5：Redis 预扣、异步落库、限流与压测证据

## 环境与口径

- 应用：Spring Boot 3.3.4，JDK 17.0.20.1
- MySQL：8.0.46，HikariCP 最大连接数 20
- Redis：Windows 服务 3.0.504，单实例
- JMeter：5.6.3，非 GUI 模式
- 压测配置：10 线程、2 秒升压、5 秒持续时间；每条路径先预热，再正式运行 3 轮
- 两条路径使用同一台机器、同一应用进程、同一 SKU、相同连接池配置

数据库路径的 201 表示订单与库存事务已经提交。Redis 路径的 202 表示 Redis 原子预扣
成功且持久化命令已写入 MySQL，订单事务由后台消费者随后提交。因此下表用于比较入口响应
能力，不能把 202 解释为订单已经完成落库。

三轮中位数：MySQL 113.30 req/s、P99 164.52 ms；Redis 342.91 req/s、P99
76.50 ms。按该次本机短时实验，入口吞吐中位数提高约 202.7%，P99 降低约 53.5%。
Redis 三轮及预热共生成 3509 条异步命令，验收时状态全部为成功；最后一轮 MySQL 可售

调度影响，第二、三轮 Redis 数字有明显爬升；正式容量结论应延长持续时间并在独立压测机复验。

## 正确性验证

- 多 SKU Lua 在修改前先验证全部库存，任一 SKU 不足时不产生部分扣减。
- 订单号作为幂等操作键，marker 保存规范化商品签名；同键不同请求返回幂等冲突。
- 覆盖 `reserve → compensate → reserve → compensate`，重复补偿不会重复加库存。
- Redis 预扣成功后写 `async_order_command`；消费者使用数据库租约、指数退避和死信状态。
- 订单、MySQL 库存预占、命令成功状态在同一事务中提交；最终失败才幂等补偿 Redis。
- 对账期望值为 `MySQL 可售库存 - 尚未落库命令的预扣数量`，避免把正常异步延迟误报为差异。
- 全量自动化测试：46 个通过，0 失败，0 错误。

## 版本边界

令牌桶时间戳由 Java 传入 Lua，且 Lua 使用 Redis 3.0 支持的命令形式，已经在当前
Redis 3.0.504 上实测。当前多键 Lua 面向单实例 Redis；若迁移 Redis Cluster，需要让
库存键与幂等 marker 使用相同 hash tag，或调整为按槽执行并设计补偿。
