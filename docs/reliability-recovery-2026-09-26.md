# 2026-09-26 可靠性修复与故障恢复验收

本记录补充同日[首轮浏览器验收](local-browser-acceptance-2026-09-26.md)，不覆盖历史结果。代码基于 `cac9236c92cf3a0550d047bddf0d6fe19481af9a` 的未提交工作区；未推送 GitHub。范围是单机单实例、专用 MySQL/Redis、五个 Java 服务和 Vue 开发服务器，不是生产部署或容量测试。

## 修复及边界

1. **R03：结算结果未知**。调用 Order 之前，Commerce 在一次 INSERT 中固定订单号、完整请求快照和初始租约。同键先读取原意图，不被当前购物车/价格覆盖；原确认金额不同仍拒绝。恢复默认租约 30 秒、自动最多 8 次，指数退避上限 60 秒。创建窗口为订单超时与配置上限 1800 秒中的较小值；截止后仅调用只读 `POST /internal/orders/resolve-create`。未查到不等于从未创建，转人工确认，不发新号。历史缺快照的记录不猜测关联；人工同键重查只读且限频。
2. **R04：创建中断**。普通 RESERVING 超过默认 60 秒后，由 5 秒扫描发现。查询和取消 CAS 都排除 Redis 命令拥有的订单；先提交 CANCELED/PENDING_COMPENSATION，再幂等释放。修复迟到未知响应直接释放有效预占的竞态：取消 CAS 未赢时读取当前结果，不释放 RESERVED/PAID 库存。
3. **R05：支付事件归属**。独立领取 token、数据库时钟 60 秒租约，成功/失败写回均要求同 owner 且租约有效。支付与事件仍在同一本地事务落库，至少一次调用 Inventory。新增[受控死信处置](../scripts/acceptance/outbox-maintenance.md)，默认预览，执行时校验事件、预期重驱代数、已支付订单及载荷，记录操作者、原因和旧重试信息。重新排队不等于投递完成。
4. **购物车并发清理**。结算前快照携带原行 ID + revision；任何加购、改量或勾选操作递增 revision。同步成功只删除仍匹配原行/版本的条目，删后重加和改回原数量均保留；后台恢复完全不清车。持久化默认 `cartCleanupRequired=true`，清理和标记均成功才置 false，覆盖异常/崩溃窗口。前端保留同键最初同意金额，未知后改车/刷新不会重新定义原意图，并显示清车核对提示。

## 故障注入与关联订单

使用仅监听回环地址、需令牌控制的代理。请求真实进入服务；验收脚本不改业务表，不调整库存，不伪造死信。只停止登记且 PID/启动时间/可执行文件均匹配的验收进程。

| 场景 | 订单号 | 核验 |
| --- | --- | --- |
| 创建已成功但响应丢失，随后重启 Commerce | `48637965557039104` | 快照/原订单号先持久化；重启后自动确认，同键仅一个订单；保留购物车；最后取消 |
| 下单在途改数量 | `48638017167949824` | 新购物车内容保留，明确清理提示，订单最后取消 |
| 下单在途删掉后重新加同 SKU | `48638018023587841` | 新行未被原请求清掉，订单最后取消 |
| 下单在途数量 1→2→1 | `48638018872934402` | revision 阻止 ABA 误删除，订单最后取消 |
| reserve 请求执行前 Order 崩溃 | `900001790418015016` | 重启自动补偿；证明取消栅栏先提交、迟到请求实际转发且被拒绝，无重新预占 |

| 支付确认接口返回 503，之后恢复 | `48638289730600963` | 支付事实保留、事件重试、库存先锁后确认；最终仅一条确认锁与一条已发送事件 |

R04 使用默认宽限，未缩短调度时间或手工重发来触发恢复。代理 hold 最长 120 秒；测试在主动放行前确认请求仍在 hold，并读取取消栅栏，避免“请求根本没执行”误判为安全。

## 内置浏览器复验

沿用首轮合成演示账号：加入保温杯 1 件，金额 89 元；控制代理丢弃创建/核对响应，页面明确提示未知。然后在页面将数量改为 2 件（178 元）、恢复依赖、刷新页面，再点击结算；返回的仍为原订单 `48638434914336784`，金额 89 元、数量 1。清理提示可见，没有按新金额创建第二单。

最后在页面取消该测试订单，观察已取消/预占已回滚。只读查询确认本账号订单总数由 3 增到 4，原结算已确认，购物车仍为 2 件；这两件是故意保留的并发编辑证据，不代表已购买。页面截图：[未知提示](evidence/recovery-2026-09-26/browser-unknown.png)、[恢复原单](evidence/recovery-2026-09-26/browser-recovered-order.png)、[取消终态](evidence/recovery-2026-09-26/browser-canceled-order.png)。

## 部署与最终核验

入口见[隔离验收说明](../scripts/acceptance/README.md)。兼容迁移为 `migration-v2-checkout-recovery.sql`、`migration-v2-outbox-lease-redrive.sql`、`migration-v2-cart-revision.sql`；停止旧写进程后执行。迁移使用独立增量校验和，不改变首轮 bootstrap 指纹，迁移与启动共享进程锁。

故障结束后恢复 Commerce→Order、Order→Inventory 直接调用，停止本轮故障代理，保留五服务、Vue 和专用依赖。最终只读结果见 [final-state.json](evidence/recovery-2026-09-26/final-state.json)：检查库存非负、库存守恒、锁数量对应、已付对应确认、已取消无残留，以及无待付/待发送事件。原 Windows MySQL 服务未停用；没有清库、删卷或移除旧演示记录。

最终累计 17 个订单：4 个已支付、13 个已取消；4 条支付事件均已发送。SKU 1001–1005 可售依次为 97、100、99、100、98，锁定均为 0；各 SKU 的可售 + 锁定 + 已确认数量仍为初始 100。统计包含首轮记录，不是本轮新增 17 单。
